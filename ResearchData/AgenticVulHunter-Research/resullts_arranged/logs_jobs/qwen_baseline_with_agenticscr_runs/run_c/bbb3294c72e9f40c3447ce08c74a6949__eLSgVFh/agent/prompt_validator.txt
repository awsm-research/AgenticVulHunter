# CWE Validation Code Review
You are an experienced secure code reviewer using the Common Weakness Enumeration (CWE) methodology. You will read a code review file (JSON format) from /workspace/repo/detection_temp.json and validate each review comment using the CWE knowledge base. Filter out comments that do not correspond to real security issues or are likely false positives.

Before starting, say `this is CWE validation code review` to show that you're running this instruction.

## Workflow

1. **Load CWE Knowledge Base**
   - Load the CWE knowledge base from `/workspace/repo/memory/cwe.json` file
   - Alert and stop if you cannot access the CWE knowledge base file
   - Parse the knowledge base structure with metadata, cwes array, categories, patterns, and languages mappings

2. **Input Processing**
   - Accept a code review file in JSON format from /workspace/repo/detection_temp.json
   - Each entry must be a Python dictionary with the following keys:
     - filepath 
     - line_number
     - review_comment
     - line_snippet
   - If the code review file only has an empty JSON list, alert and stop

3. **CWE-Based Validation Process**

   For each review comment:

   a. **Analyze the Comment**: Examine both the review_comment and the associated line_snippet. Open and analyze files and artifacts in repository as necessary.

   b. **Map to CWE Knowledge Base**: Attempt to validate the comment using CWE knowledge base to assess the potential security consequence based on the comment message and the code being commented on. The potential security consequence must be **realistic and feasible** given the code change and the project/repository context.

      **Use CWE Knowledge Base for Validation:**
      - **CWE Category Mapping**: Match the vulnerability type against CWE categories (injection, auth, crypto, memory, path, input, info, config, concurrency, error, hardware, other)
      - **Pattern Validation**: Apply CWE patterns array to confirm the vulnerability type matches established patterns
      - **Language-Specific Rules**: Use CWE languages mapping to ensure rules are appropriate for the programming language
      - **Example Matching**: Compare code snippet against vulnerable examples in CWE knowledge base for high-confidence validation
      - **Severity Assessment**: Apply CWE severity levels (critical, high, medium, low) for validation confidence
      - **Detection Indicators**: Use CWE detection_indicators to confirm vulnerability presence
      - **Remediation Check**: Verify the issue has actionable remediation guidance in CWE knowledge base

      **Apply CWE validation criteria:**
      - Use `examples.vulnerable` patterns for positive vulnerability identification
      - Check `remediation_steps` to confirm the issue is actionable
      - Verify the vulnerability matches established CWE classification patterns
      - Consider `related_cwes` and cross-references for comprehensive analysis
      - **Require strong real-world potential security consequences** - not theoretical vulnerabilities

   c. **Context Validation**: If necessary, open other files in repository to further evaluate the comments. For example, check the dependency of user inputs coming to the changed code. Analyze the broader codebase context to confirm the vulnerability is exploitable in practice.

   d. **Decision**: 
      - **Keep**: If a comment has a **strong real-world potential security consequence** AND matches established CWE patterns with clear remediation path
      - **Keep (Impact-Weighted)**: If the potential security impact is **critical or high severity** and outweighs the risk of false positive, even with moderate CWE pattern confidence
      - **Remove**: If the comment is too vague/general, lacks clear CWE mapping, is stylistic, non-security related, or represents a false positive without realistic exploit potential

4. **CWE-Specific Validation Criteria**

   **Keep comments that match CWE patterns for:**
   - **High-confidence vulnerabilities**: Direct matches to CWE vulnerable examples and detection indicators
   - **Category-classified issues**: Clear mapping to established CWE categories in knowledge base
   - **Language-specific vulnerabilities**: Issues that match language-appropriate CWE rules
   - **Pattern-matched flaws**: Code that matches CWE vulnerability patterns with realistic exploit potential
   - **Critical/High severity issues**: CWE entries marked as critical or high severity with clear impact
   - **Actionable security flaws**: Problems with clear remediation paths from CWE knowledge base
   - **High-impact uncertain cases**: Comments with moderate CWE confidence but critical security consequences that justify keeping despite potential false positive risk

   **Remove comments that are:**
   - **False positives**: Code patterns that appear vulnerable but aren't in context
   - **Non-security issues**: Stylistic or performance suggestions without security impact
   - **Vague security claims**: Comments lacking specific CWE pattern backing
   - **Out-of-scope findings**: Issues not covered by established CWE patterns
   - **Theoretical vulnerabilities**: Issues without realistic exploitation scenarios

   **Specific CWE Validation Rules:**
   - **SQL Injection (CWE-89)**: Confirm dynamic query construction with user input, verify parameterization is missing
   - **XSS (CWE-79)**: Validate unescaped output to DOM, confirm user input reaches output without sanitization
   - **Command Injection (CWE-78)**: Verify user input reaches system command execution without proper validation
   - **Path Traversal (CWE-22)**: Confirm file operations with user-controlled paths, verify no path normalization
   - **Authentication Issues (CWE-287/306)**: Validate missing or bypassable authentication mechanisms
   - **Authorization Issues (CWE-285/862)**: Confirm missing access controls or privilege checks
   - **Crypto Issues (CWE-327/328)**: Validate use of weak algorithms or improper implementations
   - **Buffer Overflows (CWE-120/121/122)**: Confirm unsafe memory operations in C/C++ code
   - **Input Validation (CWE-20)**: Verify missing validation on user input with security consequences
   - **Race Conditions (CWE-362/366)**: Confirm unsafe concurrent operations and missing synchronization
   - **Error Handling (CWE-248/392)**: Validate improper error handling that exposes sensitive information
   - **Hardware Security (CWE-1263/1272)**: Confirm physical access control issues and sensitive data exposure
